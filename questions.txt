(1) Both filter1 and filter2 examine every pixel in the image and count the number of pixels where the red value is greater than both the green and blue values. The difference is the order in which they traverse the image. filter1 iterates through the columns first and then the rows, while filter2 iterates through the rows first and then the columns. Therefore, filter2 accesses the row-major pixel array sequentially, while filter1 jumps between rows in memory.

(2) The raw data shows that filter2 generally runs faster than filter1, especially as the image size increases. For the 2048x2048 image, filter1 ranged from 0.029552 to 0.057650 seconds, while filter2 ranged from 0.015297 to 0.021533 seconds. This means filter1 had a max-to-min variation of 0.028098 seconds and filter2 varied by 0.006236 seconds. Both filters returned the same result, but filter2 was faster and its run times were more consistent in these measurements.

(3) Cachegrind shows that filter1 had 1,346,272 D1 cache misses with a 2.2% miss rate, while filter2 had only 394,726 D1 cache misses with a 0.7% miss rate. This happens because the image pixels are stored in row-major order: filter2 accesses adjacent pixels sequentially across each row, while filter1 moves between rows and jumps farther through memory. Sequential access gives filter2 better spatial locality, allowing it to make better use of the L1 data cache. This helps explain why filter2 generally ran faster in the timing tests even though both filters perform the same calculation.
